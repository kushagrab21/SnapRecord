PACKET P-002 — Measure label-extraction fidelity on dense labels, across two models and two resolutions, against user-supplied ground truth; ship schema v1

**Project:** SnapRecord, `~/Desktop/SnapRecord`, branch `main`, HEAD `737c33f`.
**Issued:** 2026-09-12 by the supervisor, after ruling P-001 ACCEPTED. **Target close:** 75 minutes from receipt.

## Context
P-001 proved the plumbing: a phone delivers a JPEG to the laptop over plain HTTP (R-0005), and `google/gemini-3.8-flash` returns v0-schema-valid JSON three times out of three at ~USD 0.0034 per photo. It proved nothing about whether the extracted text is *right*, because the only photo had no legible label (R-0010, R-0011). The product is worthless if `label_text` and `attributes` are wrong, so this packet measures that before any product code is written. Two P-001 observations need settling on the way: `capture="environment"` opened a picker, but the user-agent carried `GSA/437`, i.e. the Google app's in-app browser, not Safari — the picker may be that browser's behaviour; and `uncertain_fields` was empty on every run while `confidence` sat at 0.80–0.85, so doubt was never located to a field.

## Supervisor rulings to record before work
1. P-001 is ACCEPTED (commit `737c33f`, R-0001..R-0011). Caveats carried: the Anthropic key is unproven; OCR fidelity is unmeasured; the picker observation is browser-specific until reproduced in Safari.
2. Fidelity is measured in code against ground truth the USER types before extraction runs — never by asking the model to grade itself, and never by asking the user to grade the model's output after seeing it.
3. The extraction model, resolution, and schema for P-003 are chosen from this packet's numbers, not from preference.

## Deliverable
A committed measurement: three dense-label photos, each with user-typed ground-truth facts recorded before extraction; a 3 photos x 2 models x 2 runs matrix (12 calls) plus a 2-call resolution check, scored deterministically; `schema/item.v1.json`; and a report that names the model, resolution and schema P-003 will build on, with the per-photo cost.

## Instructions
1. **Ledger.** Append entries for ruling (1) with its caveats, and rulings (2) and (3).
2. **Capture, in Safari.** Reuse `scripts/proof-capture.mjs`. Ask the user, in one sentence, to open the URL in **Safari** (not the Google app) and photograph THREE labelled objects close up, at least one with a nutrition or ingredients panel. Record the user-agent for each upload and whether `capture="environment"` opened the camera or a picker in Safari — this is the user's statement, quoted. Downscale each to 1568px long edge as in P-001; keep both sizes. Photos stay git-ignored.
3. **Ground truth BEFORE extraction.** Before running any model on a photo, ask the user to type, for each object, exactly three facts as they appear on the label: the product name, one numeric value with its unit (e.g. an energy or weight figure), and one contiguous phrase of at least six words (e.g. the start of the ingredients list). Store them verbatim in `fixtures/ground-truth.json` keyed by capture filename, with a timestamp. Do not show the user any model output before this file is committed. `fixtures/` is test data; nothing under it may be read by extraction code or prompts.
4. **Schema v1.** Write `schema/item.v1.json`: v0 plus `field_confidence` (object, string keys -> number 0..1, one entry per top-level field the model filled) and `capture` (object, required `label_legible` boolean and `issues` array of strings such as glare, blur, cropped, distance). `additionalProperties: false` at every level. Keep v0 unchanged. Extend the hand-written validator to v1 and unit-test it with one valid and three invalid fixtures (missing required, wrong type, extra property) — a plain `node scripts/test-validator.mjs` that exits non-zero on failure.
5. **Second model.** From OpenRouter's live `/models` list, pick ONE stronger vision model with input price >= 3x gemini-3.8-flash's; record its id and both prices with the timestamp read. State why you chose it in one sentence.
6. **The matrix.** Parameterise `scripts/proof-extract.mjs` into `scripts/extract.mjs --image --model --schema v1 --out` (no framework, no new dependencies). Run each of the 3 downscaled photos x 2 models x 2 runs = 12 calls, v1 schema. Then run the 1568px AND the full-resolution version of the densest photo through gemini-3.8-flash once each (2 calls) to measure what downscaling costs. Cap: stop and report if any single call exceeds USD 0.25 or cumulative spend exceeds USD 2.00.
7. **Score in code.** `scripts/score.mjs` reads a response and the ground truth and reports, per fact: `exact` (substring of `label_text` or of any attribute value, case-sensitive) or `normalised` (match after lowercasing and collapsing whitespace and punctuation) or `missed`. Also report per response: v1 validation pass/fail, `label_legible`, `capture.issues`, `uncertain_fields`, whether any `field_confidence` entry is below 0.7, tokens, elapsed ms, USD from `usage.cost`. Output one table of 14 rows to `supervision/evidence/P-002-matrix.md` and paste it in the report.
8. **Hallucination check, AFTER scoring.** Only now show the user each response's `attributes` list and ask them to name any value that is NOT printed on the object. Record their answer verbatim per photo. A fabricated value is a finding, not a footnote.
9. **Memory and commit.** Update `ORIENTATION.md` and `RESULTS.md`; save all 14 raw responses, the matrix, the ground truth file, and the validator test output in evidence; commit `P-002: ...`; report the hash and clean status.
10. **Recommendation for P-003** from the numbers only: which model at which resolution, cost per photo, whether `field_confidence` and `capture.label_legible` behaved usefully (did low values coincide with misses?), and whether P-003 may be the product scaffold — capture page, `POST /extract`, SQLite storage of validated v1 records — or whether fidelity needs another packet first.

## Boundaries
No framework installation, no database, no new npm dependencies, no writes outside `~/Desktop/SnapRecord`, no secrets in committed files or the report, no photos committed. Model spend capped at USD 2.00 total. Do not tune the prompt between runs of the matrix — one prompt, fixed before call 1, pasted in evidence.

## Stopping condition
If the user cannot supply three close-up photos, run the matrix on however many exist and say so. If either model fails v1 validation on more than half its calls, stop the matrix, record the failures, and report — that result is itself the packet's answer.

## Acceptance
1. `fixtures/ground-truth.json` is committed with a timestamp earlier than the first extraction call's timestamp, and the report shows both timestamps.
2. The 14-row matrix is in evidence and the report, each row with model, resolution, validation, three per-fact scores, tokens, ms, and USD from provider accounting.
3. `schema/item.v1.json` exists, `scripts/test-validator.mjs` passes with its output pasted, and all 14 raw responses are in evidence.
4. The Safari user-agent and the user's camera-or-picker statement are quoted for at least one upload; the per-photo hallucination answers are quoted verbatim as the user's statements.
5. The recommendation names one model, one resolution and a cost per photo, cites matrix rows for each, states whether P-003 may be the product scaffold, and a commit hash with clean status is reported.
